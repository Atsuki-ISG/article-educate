## AI時代にプログラミングの基礎を学ぶ意味はあるのか？

AIがコードを書ける今、プログラミングを学ぶ意味はあるのか？

これは「 **基礎** 」を一つの大きなテーマとして情報発信する私がずっと悩み続けている問いです。

私の活動のターゲットは「開発をしたことがない人」が主で、「エンジニアを目指そう」というよりは「本業があって、その仕事を楽にする。質を上げる。」そういった目的観で学んでいる人が多いです。

その前提に立ったときに、その人の目的ややりたいことにもよるのですが、正直なところ、 **プログラミングの基礎を学ばずとも、AIの上手い使い方の習熟に注力すれば成果が出る可能性がある** というのが私の悩みポイントです。

もちろん、 **学んだ方が解ける課題の範囲は間違いなく増える** のですが、「全員にそれが必要か」と聞かれると、そうとも言い切れません。

そこで今回は、本業のために自動化や開発を学びたいという方に向けて、 **「プログラミングの基礎自体を勉強する必要があるのか」「その手前で成果を出すためにできることは何か」** という点について、私なりの回答をしていきたいと思います。

## バイブコーディングでどんな壁が生じるか

そもそもの、本記事の問いが発生するのはバイブコーディングを進めていると一定の壁が生じるからです。なので、どんな壁かを最初にざっくりと考えてみます。

まず一つに、シンプルにバイブコーディングで自動化を達成しきれない状態が考えられます。

例えば、エラーが出てAIに修正を頼んでも堂々巡りになってしまう、やりたいことを伝えているはずなのに意図と違うものが出来上がる、といった状況です。前回の記事で触れた「 **AIに何度言っても直らない** 」がまさにこれにあたります。

もう一つは、仮に動作するものが作れても、 **心理的に怖くて他者に提供できない** 、または属 **人性が高くなるため実運用には載せられない** などの状態も課題として存在します。

個人用のちょっとした自動化であれば、そこまでハードルを感じずとも、人に提供する、特に社内だけでなくお客さんに触ってもらうようなものを作るとなると、なかなかにプレッシャーが変わってきます。（この感じ方は人それぞれかもしれませんが）

そして、そんなブラックボックスでどうやって動いているのかをよく分かっていないものを実運用を始めた時にそのプロダクトの属人性が自分の肩にのしかかってきます。

そしてこれらの課題を解くためには、 **「AIが書いたコードを理解できるようになること」が必須...**

ではありません。

当然その課題によっても変わるのですが、 **AIのより良い使い方を学んで、それを適用するだけで解けるようになる** こともあります。  
また、AIエージェントは今も絶えず進化しており、人間側の指示の出し方が進歩せずとも解ける範囲が広がっているという側面もあります。

そういったことを念頭に、この記事ではまず「プログラミングを学ばずに壁を乗り越える具体策」を提示し、それでも乗り越えられなかった場合に「学ぶことを検討する」という順番で考えていきたいと思います。

## 「プログラミングを学ぶ」以外での乗り越え方

このラインより上のエリアが無料で表示されます。

では、プログラミングの基礎を学ぶ前に試せることとして、何があるでしょうか。私としては大きく2つの方向性があると考えています。 **AIの使い方を改善すること** と、 **コーディング以外のツールや手段を活用すること** です。

### AIの使い方を改善する

AIに修正を頼んでも堂々巡りになる、意図と違うものが出来上がる。

こういった壁は、プログラミングの知識不足だけではなく、 **AIとの付き合い方の問題** であることが少なくありません。

そして、プログラミングを学ぶ・学ばないに関わらず、 **AIコーディングツールの使い方を押さえておくこと** はどう転んでもレバレッジが効きます。

ここで例として、私が「 **ちょっと知っているだけで成果が変わる** 」と感じるポイントをいくつか紹介します。

まず一つ目は **モデル・AIエージェント** の選び方です。AIコーディングにはいろんなツールやモデルがありますが、現状ではClaudeとOpenAIが2強と言われています。

特にOpenAIのCodexはややコミュニケーションに難があったりしますが、正確性に強い評判があります。特定のツール・AIモデルでうまくいかずとも、ちょっと課金してみて、ツールを変えるだけで解けるようになる、という場面が存在し得る、というポイントは頭の片隅においておいて良いかもしれません。

次に **プランモード** です。これは開発を始める前にAIと計画を立てるモードのことです。使ってみると結構じっくり「何を作りたいのか」をすり合わせてくれます。

![画像](https://assets.st-note.com/img/1771237577-nQeJqUIGzHbYg21LRBP7cNaK.png?width=1200)

いきなり開発に入るのではなく擦り合わせる

[**一般的なワークフロー - Claude Code Docs** *Claude Code でコードベースの探索、バグ修正、リファクタリング、テスト、その他の日常的なタスクを実行するためのス* *code.claude.com*](https://code.claude.com/docs/ja/common-workflows#plan-mode-%E3%82%92%E4%BD%BF%E7%94%A8%E3%81%97%E3%81%A6%E5%AE%89%E5%85%A8%E3%81%AA%E3%82%B3%E3%83%BC%E3%83%89%E5%88%86%E6%9E%90%E3%82%92%E8%A1%8C%E3%81%86)

いきなりコードを書かせるのではなく、まず計画から始めるだけで精度が上がることがあります。これはコーディングに限らず大事な習慣ですね。

また、 **セッションのリセット** も重要です。AIは会話が長くなってくると性能が落ちてきます。

![画像](https://assets.st-note.com/img/1771237721-R8imhV4jE3Xsce5rNndUJ0kG.png?width=1200)

引用: https://www.youtube.com/watch?v=rmvDxxNubIg

「なんかこいつ的外れになってきたな」と感じたら、新しい会話セッションを始めてみましょう。もしくはClaude Codeであれば compact というこれまでの会話履歴を要約する機能があったりするので、それを手動で実行してみましょう。

これだけで解決することも少なくありません。

ちなみに、AIが長文の会話がまだまだ苦手的な話はこちらの動画で解説してあるのでよかったら見てみてください

![](https://www.youtube.com/watch?v=LzQbj5gIVgI)

そして最後に、AIが自分で作ったものがうまく動いているかを自分で確認できる **検証手段を与えること** が重要です。

AIが今何が起きているのかを把握できる方法があるかないかで、デバッグの精度がかなり変わります。

エラーメッセージをそのまま貼る、ログを共有するといったことを意識するだけでも効果がありますし、Webサイトを作っている時は、AIがそのサイトの内容や見た目を確認できる手段を持っていると着実な解決に繋がりやすくなります。(例: [https://github.com/microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp))

こういったAIの使い方について意識するだけでも、解決できる幅が広がったりします。

### そもそもコーディングじゃなくていい自動化もある

作ったものを組織に展開したいけどブラックボックスのまま渡すのが怖い、属人化してしまう。

こういった壁を感じている場合、そもそもコーディングにこだわらない方がうまくいくことがあります。ここで提案したいのが、 **やりたい自動化にそもそもコーディングが必要なのか** を見直してみることです。

例えば、以前、バイブコーディングで自動化に取り組んでいて、属人化・ブラックボックス化に悩んでいる方がいた時に、 **ワークフローツールの方が適任かもしれない** と感じる場面がありました。

n8nやDify、Google Workspace Flowsといったワークフロー構築ツールはコードよりは柔軟性が落ちますが、アプリ間のデータ連携や定型的な処理の自動化であれば、サクッと作れます。

最近はClaude Codeなどが盛り上がりすぎていて若干影が薄れている感がありますが、私はこれらのツールは今も独自の価値を提供していると考えています。

ワークフローツールの良さは、処理の流れが視覚的に見えるので何をやっているかが把握しやすいことと、 **デプロイ（作ったものをWeb上に置いて他の人が触れる状態にすること）や組織内での共有をツール側が担ってくれる** ことです。

バイブコーディングで作ったものを組織に展開しようとすると、「自分しか動かし方を知らない」「中身がわからないものを人に渡すのが怖い」という壁にぶつかりがちですが、ワークフローツールであればそのあたりのハードルが下がります。

特に「 **デプロイをどうすれば良いか分からない** 」というのはよく聞く質問なのですが、この辺りも巻き取ってくれるのは一つの大きな価値だと感じています。

もちろん、Webアプリやブラウザ拡張を作りたいといった用途にはワークフローツールは向きません。

ただ、バイブコーディングで壁にぶつかったときに **「コーディングで乗り越えなきゃ」** と思い込む前に、 **そもそも別のアプローチで実現できないか** を考えてみるのは良い習慣ではないかなと思います。

## それでも壁があるなら、AIと同じ言葉で話せるようになろう

ここまで紹介した方法を試しても、やはり乗り越えられない壁が残ることはあります。AIの使い方を工夫しても堂々巡りが解消しない、ワークフローツールでは実現できない自動化がある。

そこで「 **コードの中身を理解する** 」ことが選択肢に入ってきます。

コードを理解するための学び方には、大きく2つのアプローチがあります。 **体系的に基礎から学ぶトップダウン** と、 **実際に起きた課題から必要な知識を拾っていくボトムアップ** です。

まずトップダウンについてですが、これは書籍やオンライン教材などを使って、プログラミングの概念を体系的に押さえていくやり方です。

世の中にはたくさんのプログラミング教材があるので、それらを足掛かりにするのは良いでしょう。

また、手前味噌ですが、私が書いた『非エンジニアのためのAIコーディングの教科書』は、非エンジニアが自動化を始めるにあたって「とりあえずこれだけ押さえておけばよい」という地図を提供することをコンセプトにまとめた本です。  
コンセプトが琴線に触れればぜひ読んでみてください。

次にボトムアップについてですが、こちらは実際にバイブコーディングをしていて起きた課題を元に、 **AIと共通の語彙を獲得する** ところから始め、そこを **「仕組みの理解」への入り口** とするイメージです。

ちょうど最近、自分自身でこれを実感したことがありました。AIでSplatoon風のゲームを作ってみるというチャレンジをしていたのですが、3Dゲームの作り方に関しては素人なので、バグの伝え方があまり上手くできませんでした。

弾を打っているのにインクが塗られないというバグがあって、「インクが出ない不具合があります」と伝えても一向に直りません。

![画像](https://assets.st-note.com/img/1771239424-fdwST5zu8R63NX0svQM9FlE1.png?width=1200)

直らぬバグ

おそらくAIからすると「インクが出ない」が何を指しているのか曖昧だったのでしょう。

そこで、インクがどうやって塗られているのかをAIにコードを解説してもらいました。すると、コードの中ではインクの塗り跡を「splat」という名前で呼んでいたり、床や壁のことをどういう言葉で認識しているのかを教えてくれました。

![画像](https://assets.st-note.com/img/1771239496-ZPcIuzV2CxKQf0iW7tNBwpjY.png?width=1200)

どう作っているか説明してもらう

これらのような具体的な用語や条件を指定したところ最終的には治してくれました。

![画像](https://assets.st-note.com/img/1771239535-eYo3ZNJkQRvnwtDHflrciUqI.png?width=1200)

最終的に直すに至ったプロンプト

結局自分ではコードを完全に理解したとは言えないのですが、AIが書いたコードの中で、 **自分がやりたいことがどんな名前で表現されているのかをAIに教えてもらい** 、それを通じてより的確な言葉でエラーを表現できるようになったことで直してもらうことができました。

そして、ここで楽しかったのが、この過程で **3Dゲームがどうやって動いているのか自体への理解が少しずつ広がっていった** ことです。

例えば「インクの跡」の正体が薄い円形のメッシュ（板状のシールのようなもの）と呼ばれていることを知ったり、地面とインクのメッシュが同じ高さにあるとチラつくらしいので、それを防ぐために微妙に表示をズラす工夫を入れている、などの断片的な知識が手に入ってきました。

こういった実体験と共にした知識は、いざ **体系的に学ぶ時の強い理解の補助** となるでしょう。

このように **AIと共通の語彙を獲得していく** というところから徐々に学びを進めることが、実際の課題解決にも繋がり、楽しく学べるコツになるのではないかと思います。

## 学びに効率を求め過ぎない

ここまで、成果を出すことを主眼に置いて、段階的にどう学んでいくかという話をしてきました。

ただ、こうやって「最短ルート」を整理してみて思うのですが、 **効率的に学ぼうとすること自体が、学びの幅を狭めてしまうこともある** とも感じています。

こういった自動化の基礎は、実際に体感してみないとその価値がわからない部分があります。効率的なルートを考えすぎると、すぐに役立ちそうなものにしか興味を持てなかったり、そのルートを考えているだけで時間を消費してしまって、長期的には損をしている状態があり得ます。

いろいろ語ってきましたが、結局一番お得なのは **純粋な好奇心を持つこと** だと思っています。「これってどうやって動いてるんだろう」「へぇ、そんな仕組みなんだ」みたいな感覚を持って、学び自体をエンタメにできている状態になれると最強なんだろうなと感じています。

私も「押し付けがましくなりたくない」みたいな気持ちはありつつ、私が大事だと思っていることを"便利"な側面だけでなく知的好奇心を刺激する形で発信していけるようにしていく所存です。

というのは思ってはいつつ、冒頭でも書いた通り、ここは私自身まだ答えが出きっていない「みんな実際どう感じているんだろう」と気になっているテーマです。

皆さんはプログラミングの基礎を学びたいと思っていますか？ それとも、AIの使い方さえわかれば十分だと感じていますか？

今どんなところで壁を感じているか、どんな情報があったら助かるか、コメントなどで教えてもらえるととても嬉しいです。
